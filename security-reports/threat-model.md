# AuthAPI Repository Threat Model

## Repository Scope

AuthAPI is a Node.js/Express TypeScript authentication package. It exposes an Express router and middleware that downstream applications mount into their own server. The package manages local email/password authentication, JWT access tokens, database-backed refresh tokens, email verification, password reset, Redis-backed rate limiting and OAuth state, Google OAuth login, role checks, and verified-email checks.

## Assets and Privileges

- User credentials and bcrypt password hashes in `auth_users.password`.
- JWT signing secret supplied by the package consumer.
- Access tokens signed by AuthAPI and consumed by protected application routes.
- Refresh tokens issued to clients and hashed in `auth_token.refresh_token_hash`.
- Password reset and email verification tokens stored as hashes in `auth_users`.
- OAuth account bindings in `auth_accounts`, especially `(provider, provider_account_id) -> user_id`.
- OAuth state values stored in Redis and used to bind callbacks to login starts.
- Resend API keys and OAuth client secrets supplied through `AuthConfig`.
- PostgreSQL data integrity across `auth_users`, `auth_token`, and `auth_accounts`.

## Trust Boundaries

- Public HTTP boundary: all auth routes receive attacker-controlled bodies, headers, and query strings.
- Middleware boundary: downstream applications rely on `protect`, `requireRole`, and `requireVerifiedEmail` to enforce route access.
- Database boundary: repository functions must use parameterized queries and preserve revocation/account-linking invariants.
- Redis boundary: rate limiting and OAuth state depend on correct key construction, expiry, and one-time use.
- OAuth provider boundary: Google profile and token responses are external inputs and must be validated before local account linking.
- Email provider boundary: verification and reset URLs are sent to a third-party API and must not leak secrets.
- Package-consumer boundary: `AuthConfig` is developer-controlled but can be misconfigured; the package should fail closed where possible.

## Attacker-Controlled Inputs

- JSON bodies for register, login, logout, refresh, forgot-password, and reset-password.
- Authorization headers for protected routes.
- OAuth callback query parameters: `code`, `state`, and provider errors.
- Email addresses, usernames, roles, passwords, refresh tokens, reset tokens, and verification tokens.
- Request IP data used by rate limiting, subject to proxy configuration by the host app.
- OAuth provider profile fields including email and display name.

## Security Invariants

- Raw passwords, reset tokens, verification tokens, and refresh tokens must never be stored or returned.
- Refresh token rotation must make the old refresh token unusable after a successful refresh.
- Logout and password reset must invalidate relevant refresh-token state.
- OAuth state must be generated by AuthAPI, expire quickly, be verified on callback, and be one-time use.
- OAuth account linking must bind by stable provider account ID first, not only by email.
- Access-token payloads must contain only intended authorization facts and must be signed with the configured secret.
- `requireRole` and `requireVerifiedEmail` must only trust `req.user` set by successful JWT verification.
- Repository queries must remain parameterized.
- Rate limiting must fail predictably and not allow unlimited guessing of passwords/reset flows.

## High-Impact Failure Modes

- Authentication bypass through malformed Authorization parsing or unverified JWT payloads.
- Account takeover through OAuth callback/state weakness, unsafe provider-account linking, or password reset token misuse.
- Refresh-token replay because rotation/deletion does not happen atomically enough for the intended model.
- Sensitive token leakage through API responses, logs, email HTML, or database storage.
- SQL injection in repository functions.
- Role or verified-email authorization bypass through missing middleware ordering or incorrect JWT claim checks.
- Denial of service or brute force caused by missing or incorrectly configured rate limiting.
- Insecure package defaults or unclear configuration that make consumers deploy unsafe setups.

## Assumptions

- Host applications use HTTPS in production.
- Host applications store `jwtSecret`, OAuth secrets, email API keys, and Redis/Postgres credentials securely.
- Host applications mount `express.json()` before the router when using JSON endpoints.
- Redis is required for the current OAuth state implementation.
- PostgreSQL supports `pgcrypto` or the migration can create it.
